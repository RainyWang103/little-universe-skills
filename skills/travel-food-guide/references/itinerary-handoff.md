# 与行程交接

输出可被旅行规划师直接粘贴的块；不夺取日程主权。

## 定稿门槛（硬规则）

- **未定稿**分析与候选比较**只留在美食文档**；不得未经用户确认塞进行程 HTML。
- 仅当用户**明确定序**或明确说「可写回」后，才向旅行规划师交接：**主推＋短备选＋必做备注**（与决策层一致）。
- **已排除店不得悄悄回到主推**；若需复活，须在决策层写明原因并再经用户确认。
- 决策层状态仍为「未定稿」时，交接块最多标「仅参考／未定稿」，不宣称可嵌行程。

## 交接字段（每店）

- 店名（当地名）与简短中文标签；多门店写清哪一家
- 地址或可靠定位描述（无核实地址则标明不可导航；禁止聚合站黄页号码定稿）
- 建议用餐窗口（当地时间）与用餐时长估计
- 门到门缓冲建议（相对前后景点，粗粒度）
- 预订状态标签：未查／需订／建议提前 N 天／仅现场／用户已订（仅在用户确认后）
- 优先级：主推／备选／下雨或疲劳替换
- 备注：过敏确认、季节菜、休息日、必做备注（少盐、电话订等）

## 配合方式

- 旅行规划师负责整天排程与交通；本 skill 负责餐饮取舍与卡片深度。
- 冲突时陈述餐饮侧利弊，由用户或规划师改日程，不单方面改掉已订硬约束。
